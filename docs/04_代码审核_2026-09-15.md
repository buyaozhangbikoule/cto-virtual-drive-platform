## 1. 【高】V/I 硬约束从不触发（HANDOFF 第 2 节检查点一）

`allowed_amplitude()` 写成：

```python
a = np.minimum.reduce([np.ones_like(...), v_limit / V(f), i_limit / I(f)])
```

形式上是 HANDOFF 推荐的「写法 B」，但 `np.ones_like(...)` 这一项把幅度额外封顶在 `a <= 1`，
而 `a = 1` 对应校准冻结的源幅度 `SOURCE_A1_VRMS = 6.2174 Vrms`。

标称点上 `a=1` 恰好给出 100 Vpp / 5.000 mA，而软限值是 130 Vpp / 5.5 mA：

```
到软压限余量 1.300x ／ 到软流限余量 1.100x ／ 单位幅度上限 1.000x  -> 最小者是 1.000
```

**实测结果：34/34 个场景中，最优频率处的绑定约束都是 `a<=1`，V/I 保护一次都没有触发。**

后果有三条：

1. 平台实际运行在「写法 A」（源幅度受限）而不是「写法 B」。
   这正是 HANDOFF 第 2 节列为最严重的建模错误。
2. 标称点上被白白放弃约 **1.95 倍**功率：当前最优 170.0 mW，
   若推到硬 V/I 包络（160 Vpp / 6 mA）可达 **330.8 mW**。
3. 第 4 周「功率限幅」任务**没有任何可限的东西** —— 限幅状态机、软/硬折返、
   `VPP_HARD`/`IRMS_HARD` 在当前标定下全是死代码；
   验收指标「V ≤ 160 Vpp 零越界 / I ≤ 8 mA 零越界」被平凡满足，等于没测。

需要说明：源幅度冻结是 `stage2_控制源幅度校准.json` 里**明确写下的规则**
（"freeze this Thevenin source amplitude; protection may only reduce it"），
所以这是一个**有意的设计决定**，不是笔误。但它与「最大有功功率」这个控制目标直接冲突，
也使限幅子系统无法被验证。

**建议**：把「源幅度冻结」和「推到 V/I 约束」做成一个显式开关（例如 `drive_mode="FROZEN_A1" | "PUSH_TO_LIMIT"`），
两种口径各跑一遍并同时上报。冻结口径回答「现有功放下能做到什么」，
推限口径回答「器件耐受允许做到什么」——计划书问的是后者。
在任一口径下，`p_rm_W` 与 `p_port_W` 完全相等（C0 无损），功率定义本身没有歧义。

## 2. 【高】扫描窗口够不到两个已声明场景

`local_scan()` 的三级扫描是「当前频率 ±50 kHz / 5 kHz → ±5 kHz / 1 kHz → ±1 kHz / 0.1 kHz」。

先说好消息：**三级细化本身是够用的**。基线功率峰的 FWHM 实测 1736 Hz，
粗扫步长 5 kHz 确实比整个峰还宽 2.9 倍，粗扫单级捕获率在 12%~98% 之间乱跳；
但第二级 1 kHz 步长小于 FWHM，能把粗扫的失手捞回来。
从 0.9 MHz 起扫，**32/34 个场景最终捕获率为 100.00%**。

问题出在窗口宽度，不是步长：

| 场景 | 结果 fs | 相对 0.9 MHz 偏移 | ±50 kHz 可达 | 最终捕获率 |
|---|---:|---:|:--:|---:|
| `CASE_LM_P20` | 0.82158 MHz | 78.4 kHz | 否 | **0.10%** |
| `CASE_CM_P20` | 0.82158 MHz | 78.4 kHz | 否 | **0.14%** |
| `CASE_LM_P10` | 0.85812 MHz | 41.9 kHz | 是 | 100% |
| `CASE_FS_M5` | 0.85500 MHz | 45.0 kHz | 是 | 100% |

原因是 Lm 或 Cm 单独 +20% 会让 `fs = f0/sqrt(1.2)`，即下移 78.4 kHz，超出 ±50 kHz 窗口。
控制器只能在窗口内锁到一个非谐振点，拿到 **千分之一**的可用功率，
而 oracle 在 0.82140 MHz 上是够得到的（仍在 0.8–1.0 MHz 带内）。

这两个场景**没有出现在闭环调度表里**（`SCENARIO_ORDER` 只含 7 个场景），
所以现有批次不会暴露该问题 —— 这与 README 已声明的
「现存批次不足以进行统一三策略正式排名」「尚未完成统一全场景闭环验收」一致。
本报告的贡献是把这个已知缺口**定位到具体的两个场景并给出量化后果**。

**建议**：粗扫窗口至少覆盖 ±80 kHz（或直接按 `F_MIN..F_MAX` 全带粗扫，
2001 点 × 100 Hz 的代价在准稳态模型里可以忽略）。
若要保留 ±50 kHz 的时间预算论证，则必须把 `LM_P20`/`CM_P20` 明确标注为
「超出控制器捕获范围的已知失败场景」，而不是留在 34 场景表里当作已覆盖。

## 4. 【高】相位归零在带内有三个稳定吸引子

`run_phase_ablation.py` 的更新律是

```python
update = clip(gain * error * np.sign(slope), -MAX_UPDATE_HZ, MAX_UPDATE_HZ)
```

其中 `error = target_phase - phase`。`np.sign(slope)` 这个符号校正的作用是
**让每一个相位零点都变成局部稳定的吸引子**（无论该点 dφ/df 是正是负）。

基线场景下 `phase(Zin)` 在带内有 **3 个零点**：

| 零点 | dφ/df | 该点功率 | 占峰值 |
|---:|---:|---:|---:|
| 0.89707 MHz | +28.9 °/kHz | 10.18 mW | 5.99% |
| 0.89999 MHz | −82.9 °/kHz | 169.99 mW | **99.99%** |
| 0.90696 MHz | +15.8 °/kHz | 1.88 mW | **1.11%** |

以 gain = 5 Hz/deg 实际仿真该更新律，收敛结果完全由初值决定：

```
起点 0.8900 MHz -> 锁定 0.89707 MHz ->   5.99% 功率
起点 0.9000 MHz -> 锁定 0.89999 MHz ->  99.99% 功率
起点 0.9020 MHz -> 锁定 0.90695 MHz ->   1.11% 功率   <- 距标称仅 +2 kHz
起点 0.9200 MHz -> 锁定 0.90696 MHz ->   1.10% 功率
```

**正确吸引域窄到 0.9000–0.9020 MHz 之间**：标称频率偏 +2 kHz 起步，
相位控制器就会稳稳锁死在一个只有 1.1% 功率的点上，而且相位误差显示 −0.099°，
按「|φ| ≤ 5°」的验收指标**判定为合格**。这是最危险的一种失效：指标全绿，功率全无。

**建议**：
1. 相位策略必须附加功率有效性判据（例如锁定后功率低于 oracle 的某个比例即判为伪锁定并重扫），
   不能只看 |φ|。
2. 报告里应当把「三吸引子 + 窄吸引域」作为**相位跟踪策略的固有缺陷**写出来，
   这正是计划书第 3 周要求的「最大有功功率 vs 最小绝对相位误差」对比中,
   相位法应当失分的具体机理。

## 5. 【中】两条验收指标在 16/34 场景下不可兼得

HANDOFF 第 6 节同时要求「稳态输入相位误差 |φ_in| ≤ 5°」和「有功功率 ≥ oracle 的 90%」。

在最大功率点上实测输入相位，**16/34 个场景超出 ±5°**：

| 场景 | 最大功率点的 φ_in |
|---|---:|
| `CASE_FS_M1` | −5.3° |
| `CASE_FS_M3` | −23.6° |
| `CASE_FS_M5` | −41.5° |
| `CASE_LMATCH_P10` | +36.8° |
| `CASE_COMBINED_HIGH` | −40.0° |
| `CASE_LM_P20` | **−58.4°**（最差） |

这不是 bug，是物理：匹配网络在标称点设计后固定，一旦 fs 漂移，
「输入端匹配」与「换能器机械谐振」就不再是同一个频率。
但它意味着**这两条指标不能作为并列的合格线**——按字面执行，
控制器在近一半场景下必然被判不合格，或者被「修」成去追相位从而毁掉功率（见第 4 节）。

**建议**：把 |φ_in| ≤ 5° 降级为**仅标称场景**的指标，或改为「记录值」而非「合格线」；
扰动场景下的合格线应当只保留功率捕获率。两者的差距本身要量化上报，
这是计划书明确要求的研究结果。

## 6. 确认没有问题的部分

以下几项逐条查过，结论是**正确的**，不需要改：

- **匹配网络在扰动后没有被重新设计**。`_case()` 默认 `matching=BASE_MATCH`，
  只有显式的 `Lmatch`/`Cmatch`/`inductor_Q`/`combined` 扫描才改动网络参数。
  物理上匹配网络是固定硬件，这里处理正确。
- **工作点与 HANDOFF 完全一致**：|Z(0.9 MHz)| = 7071.07 Ω，100.000 Vpp，5.0000 mA rms。
- **BVD 参数自洽**：设计 JSON 的 `Lm` 反推 Qm = 800.00，与模型使用的 800.0 精确吻合，
  `Lm`/`Cm` 零偏差。（曾怀疑此处不一致，实测排除。）
  但**数值一致此前没有任何机制保证** —— `Lm` 在三处各存一份（Qm 推导值、设计 JSON
  的 `Lm_H` 字段、LTspice 网表字面值），三者相同仅因由 `design_stage2.py` 在 Qm=800 下
  同源生成，而 `Lm_H`/`Cm_F` 是**从未被读回的死字段**。已于 2026-09-15 修复，见第 9 节。
- **能量守恒**：`power_balance_error_W` 残差 −1.1e-16 W，机器精度。
- **与 LTspice 的一致性远超判据**：`stage2_audit.json` 在 20001 个频点上
  最大阻抗相对误差 1.4e-7、最大相位误差 6.7e-6°，计划书判据是 <0.1%，余量约 3 个数量级。
- **Rm 类扰动不可跟踪**：`CASE_RM_P50` 跟踪增益 1.0000×，
  与 HANDOFF 结论②「频率漂移可跟踪，损耗变化不可跟踪」一致。这个负结果是对的，值得保留。
- **单位口径一致**：`vport_vpp = |v_port| * 2 * sqrt(2)`，相量按 RMS 等效解释，
  与模块 docstring 声明一致，未发现 Vpp/Vrms 混用。

### 关于 Qm（HANDOFF 检查点二）

Qm **没有**被写死成单一值，`CASE_QM_{500,800,1000}` 是显式扫描变量，检查点二形式上通过。

但需要指出口径差异：本项目基线 Qm = 800，对应 Cm/C0 = 0.00438、
反谐振 fp − fs 仅 1.97 kHz、谐振带宽 fs/Qm = 1125 Hz；
而 HANDOFF 假设 Cm/C0 = 0.1、建议扫 Qm ∈ {10, 30, 100}。
两者都是同一个单参数族的成员（本项目取 Qm=800 这一档，数学上自洽），
但物理图像差别很大：本项目的谐振**极其尖锐**。

因此 HANDOFF 第 3 节的绝对功率与增益表（320/429/450 mW、453 mW 天花板、8 mA 上限）
**不适用于本仓库**（本仓库硬上限是 6 mA，V·I 天花板 339 mW）。
交接时不要把两套数字混用。

另外 `{500, 800, 1000}` 只是 ±25% 的窄扫。HANDOFF 的核心论点是
「跟踪收益由 Qm 主导，Qm 是实测阶段第一优先」，
若要支撑这一论点，建议补一档数量级更低的 Qm（如 100）作对照。

## 8. 建议的处理顺序

1. **第 4 节（相位伪锁定）** —— 指标全绿但功率全无，最危险，且改动很小（加功率有效性判据）。
2. **第 1 节（约束口径）** —— 决定整个课题的功率结论和第 4 周限幅任务能否被验证。
3. **第 2 节（扫描窗口）** —— 改一个常数即可，但不改就必须在场景表里标注失败场景。
4. **第 5 节（验收指标互斥）** —— 改文档而非改代码，但必须在正式验收前定稿。
5. **第 3 节（电缆电容）** —— 影响绝对功率量级，属于建模范围扩展，可安排在下一阶段。

## 9. 已实施的修复（2026-09-15）

针对第 6 节指出的「三份 `Lm` 副本无一致性保证」，做了三处改动。
**模型数值行为逐位不变**：34 个场景在 20001 个频点上的
`p_rm_W`/`vport_vpp`/`phase_deg`/`|z_in|` 求和校验和改动前后完全相同
（SHA256 `2e8707d0…f8f3c`）。

### 9.1 新增参数登记表

`active_stage3_5/bvd_parameters.json`。`Qm` 原本硬编码在 `model_v2_1.py` 里，
现移入此表并标注为「假设基线值」，使登记表真正覆盖全部 BVD 参数
（计划书第三章「参数原则」）。

登记表**不复制** `C0`/`Rm`/`fs` 的数值，而是用 `sha256` 钉住历史设计 JSON，
说明每个参数的来源与类别。这样既避免制造第四份副本，也防止历史文件被静默修改。

> 为什么不直接改 `stage2_匹配设计参数.json`：该文件被 `FILE_MANIFEST.json` 和
> `GIT_CONTENT_INDEX.json` 的 sha256 收录（`6a73eec8…`），修改它会破坏交接包校验，
> 也违反「历史批次不被覆盖」的约定。

### 9.2 模型加载时强制一致性断言

`model_v2_1._assert_bvd_consistent()`：由 `Qm` 推导的 `Lm`/`Cm` 必须与设计 JSON
存储值在 1e-12 相对误差内一致，否则**抛 `ValueError` 拒绝加载**，而不是静默继续。

已用沙盒副本验证：把 `Qm` 改成 810 会立即触发，报错文本直接指出
「很可能改了 Qm 但没有重新生成网表」并给出两条修复路径。

### 9.3 一致性回归测试

`workspace/CTO_virtual_drive_platform_v2_1/tests/test_bvd_parameter_consistency.py`，
7 个用例，只读、不写任何结果目录、不调用会覆盖历史批次的 `main()`：

| `test_derived_lm_cm_match_design_json` | 副本① vs 副本② |
| `test_design_json_sha256_pinned` | 历史设计 JSON 未被静默修改 |
| `test_netlist_matches_active_model` | 副本①② vs 副本③，覆盖网表全部 9 个元件 |
| `test_stage2_audit_record_still_claims_pass` | 历史交叉验证记录未被改写以掩盖回归 |
| `test_active_model_matches_ltspice_raw` | 逐频点 RAW 比对（`.raw` 不在 Git，默认跳过） |

当前结果 **6 通过、1 跳过**。已做反向验证：把 `Qm` 改成 810 后
`test_netlist_matches_active_model` 等用例立即失败。

`test_registry_declares_qm` **刻意不断言 Qm 等于 800** —— Qm 是第一扫描变量，
把它钉死会挡住合法的 Qm 扫描；要守的不变量是三份副本一致，而不是某个具体数值。

### 9.4 对 Qm 扫描的直接影响

这组改动的实际意义是：**「与 LTspice 吻合到 1.4e-7」这个结论目前只对 Qm=800 成立。**
一旦按建议把 Qm 扫成跨数量级的多档，每个非 800 的 Qm 都会让 Python 偏离 stage2 网表。
现在这件事会**在模型加载时就报错**，而不是等到有人发现交叉验证已经悄悄失效。

因此 Qm 扫描的正确做法是：逐 Qm 用 `design_stage2.py` 重新生成设计 JSON 与网表，
逐 Qm 重跑本节的一致性测试，而不是只改登记表里的一个数字。
