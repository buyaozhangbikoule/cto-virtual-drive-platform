## 2. 隔离性与代码核对

**隔离干净。** `candidate.py` 只导入 `dataclasses.dataclass` 与
`controllers` 的 `ScanBudget, phase_update, scan, valid_measurement`。
全文检索 `model|scenario|case_id|reference|optimum|settled|segment_index|metrics|schedule`
的唯一命中是首行文档字符串自述那句话。不读场景 ID、段边界、离线最优表或验收计数。

**`m.time_us == now` 不是 off-by-one。** `engine.py` 在 `self.t = stop` 之后构造
`Measurement(self.t, ...)`，`time_us` 是动作**终点**，所以 `io.control` 返回后
`last.time_us == io.time` 成立。该条件实际起到的作用是「只用当前这一拍的测量」，正确。

**`run_scan_end` 对 `run_policy` 的约 45 行复制是有理由的，不算堆砌。**
协议要求正式源不动、单因素改动，复制一份冻结副本比给正式策略加分支更安全，
而且复现结果逐位相同证明复制无偏差。

### 确实存在的代码问题（都不影响结论）

1. **文档字符串缩进顶格**：`run_phase_recovery` 1 行、`run_scan_end` 2 行。纯外观。
2. **`eligible` 算完即弃**：`gate.active` 为真时第一次计算的结果立刻被
   `gate.ready(...)` 覆盖。无害，但读起来会误以为两者有合取关系。
3. **`gate.ready()` 是带副作用的查询**：它同时推进两样本窗口、改 `self.active` 并返回 bool，
   且写在赋值表达式里。此处安全（每拍只调用一次），但重构时极易踩。
4. **`previous: object = None`** 未加类型，应为 `Measurement | None`。
5. **等待期间无事件**：门控开着但未就绪时不发任何事件，长等待在事件流里不可见，
   直到 `CENTRE_RECOVERY_COMPLETE` 才由 `wait_us` 补上。可观测性的小缺口。
6. **探针失败路径不开门控**：`PHASE_NO_NEW_CENTRE_RETURN` 分支（实测 8 次，
   正好等于探针失败数）直接返回旧中心而不进入恢复等待，于是下一拍可能立刻再探。
   连续失败时「探针→改频三次→幅度被钳」的棘轮会重新出现。
   本日程上 8 次未造成可观测损害，但这是设计上的残留路径。

## 3. 门控自身的行为（README 未报）

| 事件 | 次数 |
|---|---|
| `CENTRE_RECOVERY_BEGIN` | 101 |
| `CENTRE_RECOVERY_COMPLETE` | 101 |
| `CENTRE_RECOVERY_TRUNCATED` | 0 |
| `PHASE_NO_NEW_CENTRE_RETURN` | 8 |
| `PHASE_RECOVERY_INVALID_MEASUREMENT_WAIT` | 6 |

**101 次开门 101 次关上，12 段日程上零悬挂。** 恢复等待时长：
最小 37.0 ms、中位 37.0 ms、最大 377.0 ms、合计 5297.0 ms。

中位恰为 37 ms 有解释：探针在格点内结束（例如 20k+3 µs），
之后需要两个格点样本才满足判据，即 20(k+2) − (20k+3) = 37 ms，是理论下界。
**也就是说多数情况下幅度在改频后的第一拍就已到平台**（满幅或被软限钳住），
门控没有多等；只有真正需要升幅时才拉长到百毫秒量级。这是个好设计证据。

## 5. 一处前瞻风险：开门判据要求幅度「完全相等」

```python
if (p is not None and m.time_us-p.time_us == self.tick_us
        and abs(p.frequency_Hz-target) <= 1e-7
        and abs(m.amplitude-p.amplitude) <= 1e-12):
```

在当前模型下这是安全的：场景分段常数，门控期间频率不变，
故 `wanted = min(requested_a, soft_new)` 恒定，升幅 `min(wanted, old_a + rate·dt)`
必然在有限拍内**精确**到达 `wanted` 并停住，相邻两样本必然完全相等。
101/101 的闭合率就是这个论证的经验印证。

但本仓库 README 把**动态负载反馈**列为尚未完成项。一旦负载在段内连续变化，
`soft_new` 随之连续漂移，幅度可能每拍都略有不同而**永远不精确相等**，
门控就会整段悬挂、一次探针都不发。

对方 README 第 8 节第 1 条提到要在「测量噪声／延迟」下验证，方向对，
但没有点出这个具体失效模式。建议把判据从「完全相等」改为**「不再上升」**：

```python
and m.amplitude <= p.amplitude + tol
```

我方 L2 用的正是「不再上升」（`last.amplitude > a_prev + 1e-12` 则继续等）。

> **〔已改正 2026-10-15〕本节的建议撤回。** 「向下漂移时仍能开门」不是优点而是缺陷：
> 构造序列 0.50 → 0.49 → 0.48 下，「不再上升」在**第 2 点就放行**（幅度仍在下降），
> 而近乎相等判据不放行。**「正在下降」不等于「已经恢复稳定」。**
> 两种判据各有失效方向：近乎相等怕持续微抖（0.50→0.5+1e-10→0.5+2e-10 两者都不放行），
> 不再上升怕下降。正确做法是另立单因素候选，用可比较样本、允许变化率、
> 有限等待与明确降级动作的组合验证，而不是把 `<=` 单行替换。见 `review/23` §1.3。
*此处为模糊推测内容*：该差异在动态负载下的实际影响本轮未测，
因为当前模型无法产生段内连续变化的负载。
